# T01 企业级遗留单体到 Go 微服务的闭环重构

## 目标合同

将一座缺少文档、体量可达数十万行的 Java 单体后端，重构为可独立发布的 Go 微服务拓扑：边界清晰、契约可测、数据可迁移、流水线可重复。

本轮 **不** 自带版权受限的真实企业仓。你必须在隔离工作区里自举一个有代表性的单体（订单 / 库存 / 结算至少三块耦合），再对它做重构。规模以「能暴露错误切分」为准，而不是行数竞赛。

## 世界与约束

- 只写本任务工作区。durable、content、git 都不得离开该根。
- 用户不会替你执行 `/swarm` 或任何工具。
- 测试失败必须归因：架构切分错误，还是转换/语法/契约错误。禁止用「以后再测」结束。

## Peer 角色（对等，谁设计谁负责）

按需要自行 `write_content` 清单 → `register_participant` → `activate_participant`。建议能力而不是固定编制：架构分析、依赖拓扑、Go 生成、单测、流水线、数据迁移。编制可增可减，但 **至少 3 个非 initiator 的 active peer**。

## 协作与反馈环

单测或契约失败时，测试 peer 必须把失败写回共享世界（artifact + 协调事件），生成/架构 peer 据此改切分或改代码，再测。这是循环，不是流水线一次通过。

## Wave-1 本轮必须交付（检查点只看这些）

写在 `artifacts/`：

1. `architecture.md` — 原单体耦合图、目标服务边界、失败归因规则。
2. `artifacts/legacy/` — 自举的 Java 风格模块（可为精简伪代码 + 包结构），足以说明跨模块事务。
3. `artifacts/services/` — 至少一个可编译或可静态检查的 Go 服务骨架 + `*_test.go` 或等价测试。
4. `pipeline.md` — CI 从构建到迁移的步骤（真实可执行脚本优先）。
5. `feedback-loop.md` — 至少一次「失败 → 归因 → 修改 → 再验」记录。

## 禁止

改写 `checkpoint.json`、本套件 PROTOCOL、或评分源码。不要只在对话里列出角色而不 activate。
